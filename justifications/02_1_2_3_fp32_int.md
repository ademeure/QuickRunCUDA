### Verdict

## ADDENDUM 2026-04-23 — A3/A4 HFMA2 SASS confirmation (`tests/bench_hfma_scalar.cu`)

Tested all four MODES via auto-dumped SASS:

| MODE | PTX | SASS emitted | HFMA2 count in loop |
|-----:|-----|--------------|---------------------:|
| 0 | `fma.rn.f16` (SCALAR) | **HFMA2** | 33 |
| 1 | `fma.rn.f16x2` (PACKED) | **HFMA2** | 33 |
| 2 | `fma.rn.bf16` (SCALAR) | **HFMA2.BF16_V2** | 33 |
| 3 | `fma.rn.bf16x2` (PACKED) | **HFMA2.BF16_V2** | 33 |

✅ **Catalog A4 claim CONFIRMED**: "FP16 via HFMA2 = no extra throughput on scalar path; compiler packs into HFMA2 anyway."

**Scalar fp16/bf16 paths emit the SAME packed HFMA2 SASS as the explicit f16x2/bf16x2 paths** — there is no scalar HFMA1 in the ISA on Blackwell sm_103a. The compiler folds the scalar path into HFMA2 with both halves computing the same value (so throughput per useful FLOP is half of true packed, but instruction-rate is identical).

**Implication for catalog:** the "scalar fp16 throughput = 35.2 TF" measurement is actually executing HFMA2 with redundant lanes — it's the right SASS but the user only consumes one half. To get the catalog's claimed 70.4 TF for fp16, you MUST use `fma.rn.f16x2` (or the C++ `__half2` operator overloads).

This also explains catalog §27's "scalar bf16 add/fma (via PRMT+HFMA2) ~20000 GOps" entry — PRMT to combine pairs, then HFMA2.BF16_V2.
